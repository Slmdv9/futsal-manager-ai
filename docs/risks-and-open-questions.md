# Risks and Open Questions

## Resolved Decisions

- **2026-10-26 — Stack.** React Native + Expo with Expo Router, `react-native-svg` for the board, and Expo Router API routes on EAS Hosting.
- **2026-10-26 — Board rendering.** SVG with full keyframe positions per phase, interpolated between phases.
- **2026-10-26 — Seed content licensing.** Original content plus CMD Mora material used with the club's permission; the external reference sites are inspiration only, not redistribution sources. Enforced in code by `seed-content-licensing`: policy, source register, and author checklist in `docs/content-licensing.md`.
- **2026-10-26 — AI provider.** DevExpert Inference (OpenAI-compatible API, `DEVEXPERT_API_KEY`), model `chat` for session generator, variant adapter, and chatbot. Voice via `transcribe` is deferred.
- **2026-10-26 — Content storage.** Versioned JSON in the repo, validated at build time and shared by the app bundle and the API. No database in the MVP.
- **2026-10-26 — Anonymous quota.** 5 AI requests per day, keyed by Expo installation ID plus hashed IP, enforced server-side.
- **2026-10-26 — Offline.** Bundled content and board playback work offline; AI-generated sessions and variants are saved locally on the device.
- **2026-10-26 — Seed scope.** Infantil U14 fully seeded; minimum three exercises plus programming for each of the other six categories. Implemented on `2026-10-27` by `seed-remaining-categories`; the coach then asked for a full training-session shape, delivered by `seed-session-structure`: 50 exercises and seven Programming records, all `original`/`owned`, grouped as 2/3/2 per non-Infantil category and 2/5/2 for Infantil.
- **2026-10-28 — Weekly highlights.** The Explorar weekly block repeated the library, so `seed-weekly-highlights` added 21 in-house exercises in a separate `weekly` collection (three per category, one per session part) with an optional `references` citation. Library stays 50, package moves to `1.2.0`, and the five inspiration sources (four websites plus the UEFA manual) remain inspection-only citations, never licences or provenance.
- **2026-10-26 — Board Data schema.** Frozen at v1.0.0 in `docs/board-data-schema.md`: normalized 0–100 coordinates on a full 2:1 pitch, board-level tokens and static cones, per-phase positions/ball/arrows/labels, exactly one position per token per phase, strict unknown-key rejection, and a literal `schemaVersion`. Runtime validation ships with the contract; unknown versions are rejected and there are no MVP migrations.
- **2026-10-28 — Board renderer.** `tactics-board-renderer` draws one phase of a validated board with `react-native-svg` 15.16.0 inside a single accessible 2:1 wrapper: `1000×500` viewBox, field `20,10,960,480`, `x = 20 + nx/100 × 960` mapping, solid/dashed/dotted/long-dash arrows with a filled head on the end tangent, greedy 28-char × 3-line labels, greedy half-court shading only for a `half` board whose elements all sit on one side, and a ball badge offset tangent to the lower-right of its carrier token so the mono label stays readable. The renderer never reads `players`/`goalkeepers`, never invents tokens, and does not interpolate: phase playback is `board-phase-playback`.

## Implementation-Time Questions

- Retrieval approach: embeddings vs keyword search over a small curated library.
- Whether DevExpert `chat` reliably produces valid structured JSON for sessions and variants, or whether those two features need `chat-pro`.
- Quota edge cases: shared club/school networks, timezone used for the daily reset, and what happens if the installation ID changes.
- How Phase explanations and coaching cues are authored: manually, AI-drafted then reviewed, or both.
- Whether an AI-assisted variant becomes part of a session or always stays standalone.
- Where locally saved AI results live and how the coach clears them.
- Chat placement on mobile: full screen tab vs bottom sheet over the board.
- Category selection is intentionally session-only; if coaches expect it to survive an app restart, `local-ai-results-persistence` or a settings feature owns that storage decision.
- There is no week, session or scheduler model, no clock port, and no persistence for a rotating plan. Since `seed-weekly-highlights`, Explorar's "Ejercicios de la Semana" block reads the dedicated `weekly` collection (three curated exercises per category, one per session part) in fixed warm-up → main → cool-down order; it is a separate collection read, not a calendar rotation. A real scheduling feature must replace the rule and the copy.
- The Explorar AI entry is a navigation link to the existing Asistente IA tab, which still renders its `PRÓXIMAMENTE` placeholder until `ai-session-generator-ui` lands; the link passes no category context because nothing consumes it yet.
- The repository still has no React Native component-test runner. The general Explorar screen and the exercise detail screen are covered by pure view-model tests, source-structure guards, composition-wiring tests, and device smoke; `TacticsBoard` is covered by the pure render-model tests plus a source-text guard. Visual board regressions (stroke widths, dash rendering, overlap, clipping) are only caught by eye, so adopting a Jest-based RNTL/visual runner is its own feature-sized decision before more interactive board screens land.

## Assumptions

- Coaches will use the app on a phone/tablet, sometimes on the pitch, so mobile legibility, offline access, and fast load matter more than desktop density.
- A curated seed library is higher quality and lower risk than AI-generated content, and the AI can be grounded on it.
- Anonymous browsing is acceptable as the default acquisition experience and reduces privacy/compliance scope.
- The prototype's four screens are the correct MVP surface; "Mi Club" is a locked next-phase entry point.
- DevExpert Inference exposes the same API contract in production as in the provided example, and its cost/latency are acceptable for the quota.

## Risks

- **"Semana" copy without a scheduler.** Explorar labels the block `Ejercicios de la Semana`, but there is no week, calendar, clock port or persisted rotation state. Since `seed-weekly-highlights` the block reads the separate `weekly` collection (three exercises per category, one per session part) in fixed warm-up → main → cool-down order, so the label could still imply a scheduling feature that does not exist. Mitigation: the subtitle states the rule (`Una selección fuera de la biblioteca`), the counter shows `N ejercicios` for the weekly collection, and a future scheduling feature owns week rolls, recency and persistence.
- **AI entry point visibility.** The AI session card sits below the customer-facing hero and the category filter; on short screens a long fold could push the card out of the first view. Mitigation: keep the hero compact, avoid an extra page title, and check the rendered layout on the Android device; if it fails, move the AI card above the filter row.
- **Content quality and freshness.** The library and the weekly collection are a fixed seed; a missing or stale exercise/category now surfaces in the browse UI (and in the exercise detail route) with no fallback beyond the empty copy and the `Ejercicio no encontrado` state. Mitigation: keep the publishable-only read layer authoritative, and treat content updates as a content-package change.
- **Generated session placeholder.** The AI card points at the Asistente IA tab, which is still a `PRÓXIMAMENTE` placeholder; a coach could interpret the card as a working generator. Mitigation: the card copy explicitly says generation arrives in the next phase, and `ai-session-generator-ui` will replace the placeholder.
- **Content quality/volume.** The library is the product's core value; a thin or low-quality seed makes the AI and the board feel generic. Mitigation: every RFEF category is now session-shaped with seven library exercises and a Programming record (50 library exercises, seven records), split 2 warm-up / 3 main / 2 cool-down except Infantil's 2/5/2, and each category also carries three weekly highlights (21 more, 71 exercises in total) that do not repeat the library. Coach review of load, intensity, and age-appropriateness — especially U8 without specialist keepers versus Senior high-intensity blocks — is still pending. `tactics-board-renderer` made the hand-authored geometry visible: the first phases of the two Cadete boards inspected on device were legible; content-level geometry follow-ups are recorded in the board risks below.
- **Infantil U14 session-part assignment.** Keeping all nine Infantil drills forces 2 warm-up / 5 main / 2 cool-down instead of the 2/3/2 used elsewhere; `juego-posicion-3-1-pivote` (14 min, medium 75) opens the session and the two lowest-load drills close it. It is the only assignment that keeps two drills in each end without adding or deleting content. Open for coach review; changing it is a data-only edit to `sessionPart`.
- **Small-space geometry on the full board.** Prebenjamín and Benjamín drills use 10×10 to 20×20 spaces drawn inside the full 2:1 pitch, and two Cadete boards inspected through the renderer show content-level overlaps: `cono-salida` `(18, 50)` sits on the `pase-portero-cierre` arrow of `salida-3-1-presion-alta`, and `desmarque-cierre` sits on the pass start of `pase-y-va-carril-central`. Both are coordinates, not renderer behaviour. Mitigation: review the remaining 69 first phases and re-author cramped or overlapping geometry as a separate data-only content change; the renderer must never clamp or nudge seeded positions.
- **Legacy boards carry fewer tokens than players.** Five frozen legacy boards predate the session-structure authoring rule: `salida-3-1-presion-alta` seeds 9 tokens / 2 keepers for 10 players / 2 goalkeepers, `circulacion-cierre-ala` 6 / 1 for 8 / 2, `presion-tras-perdida` 6 / 1 for 10 / 2, `rondo-4v1-orientacion` 5 / 0 for 6 / 0, and `transicion-3v2-tras-robo` 6 / 1 for 7 / 1. Board Data `1.0.0` and `parseBoardData` accept them, and only the 24 session-structure boards plus the 21 weekly boards are asserted to have `tokens` = `players.total` with keeper count = `players.goalkeepers`. `tactics-board-renderer` draws exactly the tokens it is given and never derives counts from `players`, so these five boards visibly show 9/6/6/5/6 tokens; the fix is a separate content re-authoring change, not a renderer change.
- **Ball always sits on a token.** All 168 seeded phases place the ball exactly on a carrier token centre, so a disc drawn at the raw point would erase the mono shirt label. The renderer keeps `ball.point` exact and draws the visible badge offset tangent to the token's lower-right (`attachedTokenId`). A reviewer reading "the ball never moves" strictly must accept this documented drawing convention, or the feature must accept a covered shirt number. No seeded board exercises the free-ball path; it is covered only by the synthetic model test.
- **Edge overflow is data authoring.** Tokens, cones and labels on the touchline (`x = 0/100`, `y = 0/100`) extend past the 20/10-unit field margin and are clipped by the viewBox. Centres inside 5–95 do not guarantee full visibility: in seeded `presion-tras-saque-de-banda` phases 1–2, `r1` maps to y = 48.4 and its radius-56 ring reaches y = −7.6 (−8.6 including the 2-unit stroke), outside the viewBox. This known seed clipping limitation remains unchanged; the renderer deliberately does not clamp or inset because that would move data. Content review must consider glyph extents, not only centre coordinates.
- **Half-pitch shading is synthetic only.** `pitch.format: 'half'` is not seeded, so the graceful-degradation rule (shade the inactive half only when every token, ball, arrow label and cone sits on one side) is proven by synthetic model and component source tests and cannot be device-checked without inventing content. Do not add a half exercise just to see the shade.
- **SVG rendering inside Expo Go 58.** `react-native-svg` 15.16.0 is bundled in Expo Go and the device smoke rendered the field, tokens, cones, arrows, ball badge and JetBrains Mono labels; the arrow dash patterns were visible but are not pixel-audited, and there is no automated visual regression. iOS and real tablets remain unverified: `app.json` is portrait-only, so the 2:1 proof used two `wm size` viewports on one Android phone.
- **AI hallucination.** The board, session generator, and chatbot can produce plausible but invented tactics. Mitigation: mandatory grounding, cite source exercises, validate Board Data schema, and show provenance.
- **Anonymous AI cost/abuse.** A 5/day quota plus installation ID and hashed IP reduces abuse, but shared networks and reset tricks remain. Mitigation: server-side key, rate limiting, per-request caps, logging.
- **Structured-output reliability.** DevExpert `chat` may return JSON that fails Board Data validation. Mitigation: strict JSON schema prompts, server-side validation, retry/fallback, and escalate to `chat-pro` if needed.
- **Board rendering complexity.** SVG drawing of one phase is now implemented and device-checked, but interpolation across phases, playback state, and token motion remain non-trivial on React Native. Mitigation: the frozen schema and the pure `buildBoardRenderModel` keep geometry testable; `board-phase-playback` must add golden tests for positions and order before animating.
- **Offline/local persistence bugs.** Locally saved AI results can go stale or corrupt. Mitigation: version the local record format and test reopen-after-restart.
- **Category taxonomy drift.** RFEF brackets vs school-stage content (Chupetín) can misclassify exercises. Mitigation: explicit mapping table, no runtime guessing.
- **Legal/IP on source material.** Original content and CMD Mora permission still need to be documented in writing. Mitigation: the licence policy is now enforced in code — parsing rejects publishing `pending`/`unlicensed`/`reference-only` material and rejects `kind`/`licenseStatus` contradictions, published permission-dependent content needs attribution, and the read layer filters unlicensed records (`docs/content-licensing.md`). External reference sites stay inspiration only. `Exercise.references` stores a citation, not a licence: it is not provenance, grants no redistribution right, never satisfies the publish gate, and must not appear in `sourceName` or `attribution`. The 21 weekly records are new in-house authorship and passed a validator n-gram originality check (no 5- or 6-word overlap and no identical titles) across the four cited sources; that is a technical check, not a legal opinion, so a human review is still advisable before public release. No title, sentence, diagram, progression table or board layout may be copied. Remaining gap: written confirmation from CMD Mora.
- **Citation display obligation.** Resolved by `exercise-detail-screen`: each weekly exercise's citation renders under `Inspirado en` with its label, public URL and the disclaimer that the exercise is original Futsal Manager AI content, and records without references render no source block. The CMD Mora written-permission gap above remains open.
- **Product naming.** "Futsal Manager AI" is the chosen name. Remaining mitigation: a basic trademark/domain check and consistent relabelling of prototype screens.
- **DevExpert dependency.** A single inference provider is a single point of failure. Mitigation: keep the gateway provider-agnostic so an OpenAI-compatible fallback can be added.
- **Expo tooling advisories.** After authorized SDK patch alignment and renderer integration (2026-11-01), `npm audit --json` reports 26 moderate advisories, 0 high and 0 critical (0 low). The former four-high claim is historical, not the current audit result. Mitigation: review the moderate advisories in a separately authorized maintenance scope and rerun audit on dependency changes; no audit fix or unrelated upgrade is part of renderer integration.
- **Detail-screen disclaimer typography.** The `Inspirado en` disclaimer renders at `bodySm` (12 px), below `DESIGN.md`'s minimum 16 px body text. `docs/specs/exercise-detail-screen.md` sanctions `bodyMd`/`bodySm` for short meta and the disclaimer, and the line is a legal footnote rather than body copy, so it was accepted as a Low deviation. Mitigation: switch it to `bodyMd` in a later typography pass or record an explicit type-scale exception in `DESIGN.md`; do not let this precedent lower the 16 px minimum for body copy.
- **Explorar builds the browse model twice.** `ExploreScreen` calls `buildCategoryBrowseModel` and `buildExploreGeneralModel` also builds it internally, so a selected render performs two in-memory builds. Harmless at 71 records, but if the browse model later gains cost or state, pass a single shared model. Recorded by the `explore-general-screen` validator as an optional, non-blocking refactor.
- **32-bit Android test device.** The connected Galaxy M13 reports only `armeabi-v7a`. Expo Go 58.0.5 and the native debug build work, but the build emits Google Play's 64-bit warning because it packages only 32-bit native libraries. Mitigation: add a 64-bit Android phone or tablet to `mobile-device-verification`, and make release builds include `arm64-v8a`.
